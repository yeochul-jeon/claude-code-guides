## 주요 의사결정

### 1. Plan Mode 진입 → CLI 사실관계 먼저 검증

Eval 실행 예시는 틀린 CLI 플래그를 가르치면 안 되므로,
작성 전 `claude-code-guide` 서브에이전트로 공식 문서 기반 검증을 먼저 수행했다.
검증 항목: `-p`/`--print` 동일 여부, `--output-format` 값, `--allowedTools`·`--disallowedTools`·`--permission-mode` 플래그명, stdin 파이프, exit code 표 존재 여부.

### 2. Eval 체크 3분류 패턴 채택

advisor 지적 핵심: "stdout grep 방식은 §9이 가르치는 독립평가자 원칙과 자기모순".
결론적으로 3분류로 제시:
1. **Hook/deny 차단 검증** → exit code (결정론적)
2. **생성 결과물 정적 분석** → 파일 파싱 (결정론적, 우선)
3. **독립 Claude-as-judge** → 별도 `claude -p` 호출 (비결정적, 최후 수단)

이 순서는 §9의 "독립 평가자 원칙"과 자기일관성을 유지한다.

### 3. `--bare` 금지 뉘앙스를 가이드에 명시

CLI 검증 과정에서 발견한 중요 gotcha:
`--bare`는 hooks/skills/MCP/CLAUDE.md를 모두 스킵한다.
Hook 차단을 테스트하는 EVAL-001류에 `--bare`를 쓰면 테스트 대상 자체를 끄는 셈이므로,
이 뉘앙스를 주의 박스로 명시했다.

### 4. exit code 한계 정직 기재

`claude -p` 일반 실행의 exit code 전체 표가 공식 문서에 없다는 사실을 확인.
일부(인증 실패, stdin 10MB 초과 등)만 명시되어 있으므로 한계 박스를 본문에 추가했다.

### 5. C(EVAL-004) 포함 결정

Over-Engineering 억제 케이스(EVAL-004)를 추가할지 결정이 필요했다.
기존 EVAL-001~003은 하네스의 '도구적' 동작(파일 보호, 함수 길이, 커밋 포맷)만 다루고
'코드 품질 철학'(Simplicity First)을 검증하는 케이스가 없었다.
직전 세션에서 Over-Engineering을 패턴5로 추가한 것과의 일관성을 위해 포함.
canonical 링크로만 연결, 본문 재서술 없음.

## 대화 중 주요 논의

### 1. "보강"의 범위 — 분량 초과에 대한 판단

plan은 "+35~55줄"을 목표로 했으나 실제로는 +104줄이 됐다.
초과 원인: 3분류 각각에 코드 블록이 필요(코드 없으면 "어떻게 돌리는가"를 가르칠 수 없음).
advisor의 Simplicity First 원칙은 *불필요한* 복잡성을 피하라는 것이지,
필요한 내용을 임의의 라인 수로 잘라내라는 것이 아니다. 판단: 정당한 초과.

### 2. `--bare` gotcha 발견

CLI 검증 중 예상치 못한 발견:
`--bare`가 CI용 고속 실행 플래그로 권장되지만,
Hook 동작을 테스트하는 eval에서는 테스트 대상을 끄는 함정이 된다.
이 뉘앙스는 공식 문서에 명시되지 않은 실전 지식이므로 주의 박스로 강조했다.

### 3. exit code의 한계를 "사실"로 기재

`claude -p` exit code 전체 표가 없다는 것을 확인 후,
"exit code로 검증할 수 있다"고 단정하는 대신 한계를 명시하는 방향을 선택했다.
가이드가 틀린 정보를 가르치는 것보다 "알려진 한계"를 솔직히 기재하는 것이 낫다.
